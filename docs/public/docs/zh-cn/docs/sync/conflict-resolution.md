# 冲突解决

当多台设备同时修改同一条记录时，就会产生同步冲突。QuantaNote 提供了完善的冲突检测和解决机制，确保你的数据在多设备间保持一致。

## 冲突如何产生

同步冲突发生在以下典型场景中：

**场景示例：**

1. 你在设备 A 上编辑了一条笔记，但还没有同步
2. 你在设备 B 上也编辑了同一条笔记，并同步到了服务器
3. 当设备 A 尝试同步时，系统发现同一条记录在本地和远程都被修改了

**三路差异比较（Three-way Diff）：**

QuantaNote 使用三路差异比较算法来准确检测冲突。这个算法需要三个版本：

| 版本 | 说明 |
|------|------|
| 基线版本（Base） | 上一次同步完成时的快照 |
| 本地版本（Local） | 自基线以来本地所做的修改 |
| 远程版本（Remote） | 自基线以来服务器端的修改 |

**比较逻辑：**

- 如果只有本地修改了 → 直接推送本地版本
- 如果只有远程修改了 → 直接拉取远程版本
- 如果两者都修改了同一条记录且内容哈希不同 → 产生冲突

这种三路比较比简单的"最后写入胜出"更精确，因为它能区分真正的冲突和非冲突的并发修改。

当前 diff 以记录哈希为粒度判断冲突，因此同一条记录被两台设备分别修改且最终内容不同，就会进入冲突解决流程。手动模式下可以继续按字段选择，避免整条记录二选一。

## 冲突解决策略

QuantaNote 提供四种冲突解决策略，你可以在 **设置 > 同步** 中配置：

### Auto（自动解决）

- **原理** — 比较本地和远程版本的修改时间戳，自动选择时间戳更新的版本
- **适用场景** — 大多数情况下的默认选择
- **优点** — 无需人工干预，同步过程完全自动化
- **缺点** — 可能丢失较旧但更重要的修改

### Local-wins（本地优先）

- **原理** — 冲突时始终保留本地版本，丢弃远程版本
- **适用场景** — 你确信本地设备上的数据是最新的
- **优点** — 简单直接，不会丢失本地修改
- **缺点** — 远程设备上的修改会被覆盖

### Remote-wins（远程优先）

- **原理** — 冲突时始终采用远程版本，覆盖本地修改
- **适用场景** — 你希望服务器端的数据始终作为权威版本
- **优点** — 确保所有设备与服务器保持一致
- **缺点** — 本地的未同步修改会丢失

### Manual（手动解决）

- **原理** — 每次冲突都会弹出解决界面，由你逐条选择保留哪个版本
- **适用场景** — 数据很重要，不允许自动决定
- **优点** — 完全可控，不会意外丢失数据
- **缺点** — 冲突较多时需要较多人工操作

**策略对比：**

| 策略 | 自动化程度 | 数据安全性 | 适用场景 |
|------|-----------|-----------|----------|
| Auto | 高 | 中 | 日常使用 |
| Local-wins | 高 | 中（本地优先） | 单设备为主 |
| Remote-wins | 高 | 中（服务器优先） | 服务器为主 |
| Manual | 低 | 高 | 重要数据 |

## 手动解决冲突

当选择 Manual 策略时，每次同步检测到冲突都会弹出冲突解决界面。

**冲突解决弹窗功能：**

1. **冲突列表** — 显示所有检测到的冲突记录
2. **左右对比** — 每条冲突并排显示本地版本和远程版本的完整数据及更新时间
3. **选择解决方式** — 对每条冲突选择：
   - 保留本地版本
   - 采用远程版本
   - 按字段合并
4. **字段合并** — 普通字段可以分别选择本地值、远程值或输入手动值；记录 ID、标签 UUID 和标签关联的组成标识保持不变
5. **批量操作** — 可以一键选择全部保留本地或全部保留远程
6. **确认解决** — 确认所有冲突的选择后，点击"应用解决"按钮

**操作建议：**

- 仔细对比本地和远程版本的差异
- 对于重要的笔记内容，可以使用字段合并；手动值支持 JSON 或普通文本
- 合并结果会在服务端校验记录标识，不能借此修改另一条记录或提交删除标记
- 如果冲突数量很多，可以考虑使用 Auto 策略简化操作

## 基线和墓碑

### 快照基线（Snapshot Baseline）

基线是同步引擎的核心概念之一：

- 每次同步成功完成后，系统会生成一个基线快照
- 基线快照记录了本次同步完成时的数据状态
- 下次同步时，系统会对比当前状态与基线的差异来确定变更内容
- 每个设备维护自己独立的基线

基线的作用：

1. **增量同步** — 只同步自上次基线以来的变更，避免全量传输
2. **冲突检测** — 三路比较需要基线作为参照点
3. **断点续传** — 如果同步中断，可以从上次基线重新开始

### 墓碑机制（Tombstone）

墓碑机制用于正确处理删除操作：

- 当你删除一条记录时，系统不会立即物理删除，而是标记为"墓碑"
- 墓碑记录包含被删除记录的 ID 和删除时间
- 同步时，墓碑会被同步到其他设备
- 其他设备收到墓碑后，会删除对应的记录

**为什么需要墓碑？**

如果不使用墓碑，会出现以下问题：

1. 你在设备 A 删除了一条笔记
2. 设备 B 还保留着这条笔记
3. 设备 B 同步时，会认为这条笔记是本地新增的，并将其推送到服务器
4. 结果：已删除的笔记又出现了

墓碑机制通过保留删除标记，防止已删除的记录被其他设备"复活"。

> **提示**：墓碑记录会占用少量存储空间。QuantaNote 会在适当时候自动清理过期的墓碑记录。
